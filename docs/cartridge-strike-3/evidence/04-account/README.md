# CS3-04 account and room authority

The backend runs on the existing HTTPS pilot. The reference UI in `frontline/source/src/09j-compte.js` supplies the profile, sign-in, registration and recovery flow. Its remote account service is absent from the source. Colyseus supplies the authoritative room, seat, mode, readiness, results and host changes. The existing family settings file retains its format.

## Private storage and recovery

With family access enabled, the default database is `cs3-accounts.sqlite` beside the family settings file. A pilot without family access can set an absolute `CS3_ACCOUNT_DB`. Keep the private state directory outside the release. Only one pilot process owns the database. On the tested Pi Node 26.13, the native SQLite module uses WAL, FULL synchronous commits, foreign keys and transactions. Account deployments require the native `node:sqlite` module enabled. LAN and local gameplay use their existing account-free path.

Schema v1 contains users, hashed sessions and recovery proofs, scoped device admissions, match summaries and unique reward receipts. The v2 migration adds bounded, expiring credential-attempt records and a grant lookup index. Schema v3 adds account-bound public room admissions, personal blocks and bounded moderation reports. Session and device cookies last 30 days, are restricted to the HTTPS origin and have the Secure, HttpOnly and SameSite=Strict attributes. New passwords use salted scrypt with N=32768, r=8, p=1 and at most two concurrent derivations. Ten credential attempts per normalized account in ten minutes supplement peer and server-wide admission limits. Password changes and recovery invalidate prior account sessions. An account can retain up to sixteen session records. A deleted account's match results and reward receipts are removed with it.

For an operator-controlled backup, supply two absolute private paths. The destination must be new. A consistent SQLite snapshot is integrity-checked and published with mode 0600. Restore to a separate new file, verify the restored accounts in isolation and select the restored file at a controlled restart.

```sh
node server/account-backup.mjs backup "$CS3_ACCOUNT_DB" "$CS3_BACKUP_FILE"
node server/account-backup.mjs restore "$CS3_BACKUP_FILE" "$CS3_ISOLATED_RESTORE"
```

The rehearsal in `server/test/account-store.test.mjs` registers a fixture account, grants a device access, credits results, migrates a v1 database through v3, snapshots active WAL state, restores to a fresh path, signs into that copy and replays receipts. It also verifies that deleting the restored account leaves its original intact. Backup files contain private account data and remain outside Git.

## Room and result behavior

The invitation URL contains a one-use fragment. The entry page clears it from the address bar and exchanges it at the same origin. The ten-character short code and 256-bit link share a 15-minute deadline and one redemption. Issuing another invitation rotates outstanding links. Explicit host revocation invalidates claimed grants and disconnects those scoped members. A host credential belongs to the device bound to the connected authoritative host seat. Longstanding family or private passwords still work through the pilot and remember the device after it joins. The stable family alias survives process replacement. Transient private grants expire with the room. Signing out of a profile preserves the separate room grant. Forgetting a room drops that device's room access.

The HTTPS pilot defaults to private hosting. Set `CS3_PUBLIC_LISTING=1` to enable the authenticated public directory. The profile payload exposes `features.publicMatches` to signed-in and guest clients. A signed-in live host may explicitly publish a waiting nonfamily room while alone, before issuing invitations or admitting others. Colyseus keeps its private matchmaking transport. The account directory derives its listing from the live local authorities and returns the room ID, map, mode, population and capacity. Signed-in viewers exchange an eligible room ID for a five-minute admission scoped to that room, publication, device and account session. Joining extends that scope to two hours. The normal reservation and socket paths recheck the grant. Capacity counts existing reservations as well as connections. Full rooms, private rooms, family rooms, blocked participants and results screens are filtered. Signal loss hides the listing during the host's 15-second reserved interval. The same host can resume while current public participants stay connected. A full host departure, reservation expiry or sign-out withdraws the listing. Explicit unpublication clears public grants and disconnects publicly admitted seats.

Current participants can report a peer using a fixed reason. Reports are capped at ten per reporting account per day and 4,096 outstanding records, with a 30-day retention period and duplicate suppression. The host can see anonymous counts by current peer and reason and remove a player for the rest of that room's lifetime. Room removals are capped at 128. A player can block up to 128 accounts they meet and manage that list from their profile. Blocking as a guest leaves the shared public room. Blocking as host removes the targeted peer. Server-side filtering prevents blocked pairs from finding or joining each other's public rooms. Roster and incident references are scoped to a publication. Account export includes the owner's block names and their report reasons and dates. Deletion cascades to their moderation records.

The authority allocates a random match instance when deployment becomes active. The result transaction writes one summary and one reward receipt per participant and instance. The first admitted seat earns for its account. When it fully leaves, the next eligible tab takes over from its current counters. A signal-loss reconnect retains the same scoring period. A later join can add a new period on another team. The latest eligible period determines the win. An expired or signed-out account session cannot earn a new result. Basic match credits currently award 10 XP per kill and 25 XP for a win. Package CS3-10 owns the remaining progression rules. CS3-09 owns validated equipment, outfit and class persistence when its content and entitlements are available.

## Verification

Backend revisions `6ab359d`, `13315a7` and `a37006f` build on `adb3cdf`. Local verification used the Raspberry Pi, Node v26.13.0, temporary stores and loopback test servers. No production credentials or state entered the fixtures.

```sh
node --import ./server/register-shared.mjs --test --test-concurrency=1 server/test/account-access.test.mjs server/test/account-store.test.mjs server/test/pilot-access.test.mjs server/test/family-room.test.mjs server/test/lan-access.test.mjs
node docs/cartridge-strike-3/evidence/04-account/kdf-cost.mjs
```

The serial backend suite at `fceb7d5` passed all 18 tests in 49.6 seconds, including the independently reviewed lifecycle and recovery cases. The public-directory fixture uses three real signed-in socket clients. It verifies private and full room exclusion, host consent, moderation and removal, bidirectional block visibility, distinct participant references, explicit unpublishing, host logout and family exclusion. The score fixture runs two real Colyseus rooms with local match number one, completes a rematch on each, and verifies exactly three results for the account after the final match is played signed out. Together the fixtures exercise two separate guest/host clients, legacy passwords, scoped links, rotation, revocation, forgetting, private-room return, account registration, restart, login, recovery, export, deletion, hash concurrency, invitation expiry and durable reward replay. The independent review regression used the existing game damage and respawn rules to accumulate four kills and four deaths through a full leave, overlapping tab, grace reconnect and later team change. The result contained one win and 65 XP. The private admission fixture revoked an offline guest's room grant while its independent pilot login remained valid. The public fixture hid the listing while its host regained signal, retained the other connected player, and rejected management of private invitations while published.

A transient primary SQLite write failure stores the match receipt alongside the main database in an owner-only `.pending.sqlite` journal. This journal has its own synchronous transactions and accepts up to 64 receipts of at most 256 KiB each. A normal WAL writer lock permits account eligibility to be resolved at match completion before scores enter the journal. An unreadable account store defers eligibility resolution and retains only the server's hashed session references in the private journal. Completed results retry after five seconds and on restart. Backup folds pending receipts into the verified snapshot. Replaying a receipt after its primary commit cannot duplicate XP, recreate a deleted account, or replace private account state. If neither store accepts writes, a bounded in-memory queue retries while the process is running. A full or failed disk cannot guarantee recovery across power loss or shutdown. The isolated WAL regression held the primary write lock through match completion, backup and intentional server shutdown, verified the restored score and replayed the same receipt across restart. One summary and one reward remained.
